## 1. 结论先行

| 问题 | 结论 |
|---|---|
| 有没有现成的「字 → 五笔字根序列」数据？ | **没有**。公开数据只到「字 → 五笔码」，拆解序列要么自己生成，要么人工整理 |
| 能不能自动生成？ | **能，但需要一道反校**：IDS 结构数据给出构件分解 → 映射到 130 字根 → 按取码规则重编码 → **结果必须等于码表里的码**。一致率是可信度的量化指标 |
| 码表能不能直接用？ | 能，但许可分两档：`rime-wubi`（LGPL-3.0，保守可靠）与 `KyleBing/rime-wubi86-jidian`（Apache-2.0，宽松但底层沿用极点码表） |
| 最大的坑是什么？ | **CHISE 系 IDS 数据是 GPL-2.0 系**，如果它是 `-only` 而不是 `-or-later`，**与 GPL-3 不兼容**，混进 GPL-3 项目即侵权。改用 Unihan `kIDS`（Unicode License）可绕过 |

## 3. 汉字结构 / 拆解数据

| 来源 | 许可 | 覆盖 | 可用性 |
|---|---|---|---|
| **Unihan `kIDS`** | **Unicode License（宽松，可商用）** | Unicode 提案于 2021 年（L2/21-118R），后续版本落地，随 Unihan.zip 发布 | ✅ **首选**。字段内是标准 IDS 串，如 `好 = ⿰女子` |
| [`cjkvi/cjkvi-ids`](https://github.com/cjkvi/cjkvi-ids) | `ids.txt` 源自 **CHISE**，随其条款；其余数据 **GPLv2** | 10 万+ 字符 | ⚠️ **许可陷阱**，见 §4 |
| CHISE IDS database | GPL 系（有资料称 **GPL-2.0-or-later**，另有资料称 GPLv2） | 最全 | ⚠️ 需核实是 `-only` 还是 `-or-later` |
| 漢字構形資料庫（中研院） | 代码 GPL-3.0，**数据 GFDL 1.2 + CC-BY-SA 2.5 TW** | — | △ 可商用但带署名与传染条款，需单独评估 |
| Glyphs 插件 HanziIDSComponentExplorer 的 `ids.pdata` | 声明受 **GPL-2.0-or-later** 约束 | — | △ 与 Unihan 重复，无必要 |

**关键认知**：IDS 拆的是「**构件**」（视觉部件），不是「**五笔 130 字根**」。两者高度重合但不等价：

- IDS 的 `<component>` 可能是字根的变形、也可是跨字根的笔画组合；
- 五笔拆字遵循五条人工约定：**书写顺序 / 取大优先 / 兼顾直观 / 能连不交 / 能散不连**，还要处理末笔识别码；
- ⇒ **不能把 IDS 直接当字根序列用**，必须过一层「构件 → 字根」映射 + 规则校验。

## 4. 许可陷阱（必须写进风险表）

1. **GPL-2.0-only 与 GPL-3.0 不兼容。** 如果 `cjkvi-ids` 的 `ids.txt` / CHISE 数据确实是 GPL-2.0-**only**，那么把它并入 GPL-3.0-or-later 的亨利输入法是**许可冲突**，不是「注明来源」就能解决。只有 `-or-later` 才能升到 GPL-3。
2. **数据许可会反向锁死代码许可。** 先定数据、再定代码许可，或两者同时定；不能先写 GPL-3 再随手抓 GPL-2 的数据。
3. **衍生数据的授权不因作者声明而自动成立。** `KyleBing` 的 Apache-2.0 声明不消除「极点码表上游权利不明」的风险——规避方式是：只用其**新增/扩展词表**，不复制其单字码表；或整体改用 `rime-wubi`。

## 5. 拆字数据生成流水线（M0 待验证）

```
Unihan kIDS（结构）  ─┐
130 字根表（公开知识）─┼─▶ 构件→字根 映射 ─▶ 取码规则引擎 ─▶ 候选拆解
rime-wubi 码表（真值）─┘                              │
                                                      ▼
                                          重新编码 == 码表？ ──否──▶ 丢弃/人工
                                                      │是
                                                      ▼
                                              roots.toml（可信拆解）
```

- **字根表**：86 版 130 个字根 + 25 键位（划分口诀在现代汉语公开资料中广泛收录，属公开知识，可自行整理成数据，不依赖特定数据库）。
- **取码规则**：键名汉字（连击 4 次）、成字字根（报户口 + 首/次/末笔）、四码以上取「一二三末」、不足四码补末笔识别码。
- **反校**是关键：任何拆解只要重编码后不等于码表中的码，就判为不可信。这条把「数据质量问题」变成「可量化的通过率」。
- **验收指标**（PROJECT.md M0）：3500 常用字中，能生成**且通过反校**的拆解 ≥ 95%。达不到就退化为「只显示五笔码」，拆字延后。

## 9. 追加勘察（决策 D13：自研码表）

### 9.1 为什么要自研

五笔 86 是**公开方案**（王永民 1985 年申请专利，20 年期限早已届满）。码表不是创作性文本，而是「方案 + 拆分规则」的确定性产物——给定字根表、拆解与规则，编码唯一。因此**独立实现并生成自己的表**，在法理上比「复制一份署名 Apache-2.0 但上游权利不明的极点码表」干净得多。

配套的工程约束：

- 第三方码表**只做本地离线比对**（校验自研结果），**不进产物、不打包、不发布**。
- 生成物必须可复现：同输入 → 同输出 → 同 hash。

### 9.2 新增可用的拆字数据

| 来源 | 许可 | 规模 | 评价 |
|---|---|---|---|
| [`kfcd/chaizi`](https://github.com/kfcd/chaizi) 漢語拆字字典 | **CC BY 3.0**（署名即可） | 17,959 字，简繁双版（`chaizi-jt.txt`） | ✅ **最实用**。直接给「字 → 2~6 种拆法」，且拆法里带部首/部件变体（如 `拆 = 手斥 / 扌斥 / 才斥`），比 IDS 更接近「部件」而非「结构算子」 |
| Unihan `kIDS` | Unicode License | 全量 | ✅ 结构权威、许可最宽松，但只是构件树，需要额外映射 |

⇒ 推荐**双源交叉**：以 `chaizi` 的拆法作为候选生成器，用 `kIDS` 校验结构树是否自洽，最后用**重编码一致性**做终审。

### 9.3 简码与词组：需要字频/词频

| 用途 | 需要的数据 | 候选来源 |
|---|---|---|
| 二级/三级简码 | **字频**（同一前缀下取最常用字） | 《现代汉语汉字频率表》（[corpus.zhonghuayuwen.org](http://corpus.zhonghuayuwen.org/) 语料整理，社区有整理版） |
| 词组表 | 常用词表 | 《现代汉语常用词表（草案）》56,008 词（教育部发布，社区有文本版）；或用 [`wordfreq`](https://github.com/rspeer/wordfreq)（代码 MIT，**数据 CC BY-SA 4.0**） |
| 词组码 | 无需外部数据 | 由单字码按规则推导（二字词各取前两码、三字 1+1+2、四字以上取一二三末）——**完全可自动生成** |

> `wordfreq` 的数据是 **CC BY-SA 4.0（带 ShareAlike）**，若采用，衍生的词频文件也须以同协议发布。这与「数据独立授权」策略兼容，但要在 `NOTICE` 里写清。

### 9.4 组织原则（D12）

```
亨利输入法（GPL-3.0-or-later）
├── 代码            → GPL-3.0-or-later
└── data/
    ├── wubi86/     → 自研生成，随项目以 CC BY-SA 4.0 或 GPL-3 发布（待定）
    ├── roots/      → 自研生成（源自 chaizi CC BY 3.0 + kIDS Unicode License）→ 保留原署名
    └── emoji/      → 项目原创
```

**不要**把 CC BY 3.0 的数据「并入」GPL-3 代码文件——保持独立文件、独立 `LICENSE`、独立署名，是最省事的合规姿势。

## 10. 拼音词库（M3 追加，已落地）

| 来源 | 许可 | 覆盖 | 状态 |
|---|---|---|---|
| [`rime/rime-pinyin-simp`](https://github.com/rime/rime-pinyin-simp) | **Apache-2.0**（`LICENSE` 原文已核对） | 65,125 条（单字 17,047 / 词组 48,078）· 415 音节 | ✅ **已采用** |
| [`mozillazg/pinyin-data`](https://github.com/mozillazg/pinyin-data) | MIT | 字 → 拼音，含多音字 | 备选：只有单字、无词频 |
| Unihan `kMandarin` | Unicode License | 字 → 主要读音 | 备选：无词频、无词组 |

**为什么选 `pinyin-simp`**：它是唯一同时具备「词 + 音节串 + 词频」三样的公开数据，
而混输需要按词频排序（否则 `hao` 的候选全是随机顺序）；许可 Apache-2.0 比五笔码表的
LGPL-3.0 更宽松，与项目兼容。

**实测数据质量**（`tools/gen.ps1 -Kind pinyin` 的四项验收全过）：

| 项 | 结果 |
|---|---|
| 常见字覆盖 | 3498 / 3498 = **100%** |
| 拼音字符集 | 全部小写 a–z，零脏数据 |
| 音节数 / 最长 | 415 个 / 6 字母（`shuang`、`zhuang`、`chuang`） |
| 与五笔单字的交集 | 拼音的 17,047 个单字**全部**能拿到五笔码（码提示的数据前提） |

**已知瑕疵**：名字虽叫「袖珍简化字」，实际含大量繁体与异体字（鼥、釛、軷…），
共 1,714 条权重为 0。**不做过滤**——它们里有人名/地名用字，砍掉会让某些名字打不出来；
权重 0 会让它们排在每组末尾，不占首屏。

**装配产物**：

```
data/pinyin/
  lexicon.tsv      pinyin<TAB>word<TAB>weight   （拼音去掉音节空格）
  syllables.txt    415 个音节，每行一个
  scheme.toml      清单 + 词库哈希（装载时校验）
```

去掉音节空格的理由与代价见 `docs/dev-guide.md` §4.10。
